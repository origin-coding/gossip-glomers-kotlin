# Kafka 性能探索记录

2026-11-10：本次 5c 性能探索阶段性收尾，保留现有实现，不继续增加分块或主动等待窗口。
默认使用 `batch`，同时保留 `KAFKA_MODE=direct|hash|batch`，便于理解和对照三种写入策略。

## 本轮结论

Hash 路由将同 key 的写入集中到 owner，消除了本轮观察到的日志追加 CAS 冲突；
队列批处理利用等待 KV RPC 的时间收集后续请求，在网络延迟和写入竞争明显时产生收益。
无额外网络延迟时，平均每批仅 1.003～1.033 条，吞吐基本接近，路由和排队的收益不稳定。
增加节点也会增加转发比例，不能据此认为节点越多就越快。

代表负载 S-D：2 节点、16 并发客户端、目标 rate 1000、网络延迟 5 ms、每 key 最多写 16 条。
三种模式均通过检查，主要负载各运行 5 秒。

| 指标 | direct | hash | batch |
| --- | ---: | ---: | ---: |
| 实际成功操作/秒 | 511.6 | 413.0 | 660.6 |
| send P99（ms） | 198.01 | 195.39 | 51.80 |
| 服务端消息/操作 | 9.23 | 6.69 | 5.60 |
| 日志追加 CAS 冲突 | 1941 | 0 | 0 |
| 平均每批消息数 | 1 | 1 | 1.718 |

该负载中 batch 相比 direct：吞吐提高约 29%，send P99 降低约 74%，服务端消息开销降低约 39%。
batch 使用 898 次成功 CAS 追加 1543 条消息，最大批次为 7；无需凑满 64 条才有收益。

吞吐按前 5 秒内完成的成功操作数计算，包含 assign；延迟取前 5 秒内发起并成功的请求，使用最近秩分位数。
服务端消息/操作使用 Maelstrom 的整轮统计，包含 lin-kv 通信和最终收尾读取，口径与前两项不同。
这是单轮短测试，只用于确认收益方向，不代表长期稳态性能或最大吞吐。

## 验证范围与未完成项

矩阵计划 10 组 × 3 模式，共 30 次；实际执行 24 次，其中 23 次通过。
S-H 的 batch 返回 `unknown`（退出码 2）后脚本停止，S-I、S-J 的 6 次测试未执行，未补跑。

S-H 参数为 5 节点、16 并发、rate 1000、网络延迟 5 ms、每 key 最多写 256 条。
其 batch 记录了 564.4 成功操作/秒、send P99 57.43 ms、平均每批 1.766 条，
但这些性能数据仅作参考，不能将该次测试记为正确性通过。

异常位于 Maelstrom 0.2.4 所带 Jepsen Kafka 检查器的 `lost-write-cases`：
key `"0"` 只返回空 poll、没有任何写入时，计算出的 bound 为 -1，随后对空向量执行 `nth` 导致越界。
已经用极小的合成空日志输入复现到同一堆栈（`kafka.clj:1111`）。
独立核对历史时，1399 次成功 send 都在 poll 中找到了相同 offset 与消息，没有已确认 offset 冲突；
这项核对不替代完整检查器，原始 `unknown` 结果保留，未修改业务代码规避该问题。
